# 新能源汽车相关候选文件筛选逻辑说明

生成时间：2026-06-04 12:17 CST

对应脚本：`scripts/nev_policy_pipeline.py`

本说明解释当前流水线如何用 BeautifulSoup 和关键词规则，从法规库中初筛“新能源汽车相关候选文件”。注意：这一步只做高召回候选筛选，不等同于最终认定“新能源汽车产业政策”。最终是否属于产业政策，以及政策工具、事前/事后、供给端/需求端、支持/限制等分类，由后续本地大模型对抗判断完成。

## 1. 总体流程

每条法规文件先经过以下步骤：

1. 从 JSON 记录中读取 `detail_html` 字段。
2. 如果存在 `detail_html`，使用 BeautifulSoup 解析 HTML，并用 `get_text("\n")` 提取纯文本。
3. 如果 `detail_html` 不存在或解析失败，则退回使用 `detail_flag` 原始文本。
4. 对文本做空格和换行规范化。
5. 将 `title + 正文前 20000 字` 合并为候选判断文本。
6. 用新能源汽车强关键词、弱词近邻规则、政策语境词和误伤扣分规则计算候选分数。
7. 默认 `candidate_score >= 3` 的文件进入“新能源汽车相关候选”。
8. 对候选文件生成 `llm_body`，交给后续本地模型做严格产业政策判断。

## 2. BeautifulSoup 的作用

BeautifulSoup 不直接判断文件是否相关，它只负责把 HTML 正文变成可检索文本。

代码逻辑如下：

```python
html = record.get("detail_html") or ""
raw = record.get("detail_flag") or ""
if html:
    soup = BeautifulSoup(html, "html.parser")
    text = soup.get_text("\n")
else:
    text = raw
```

这样做的原因是法规正文经常包含 HTML 标签、表格、段落标签或网页样式。如果直接对 HTML 字符串做关键词检索，可能出现两类问题：

- 标签和正文混在一起，影响关键词窗口截取。
- 表格、段落、列表文字连接过紧，导致近邻规则误判或漏判。

BeautifulSoup 清洗后，规则判断面对的是更接近人工阅读的纯文本。

## 3. 候选文本范围

候选判断使用：

```text
标题 + 正文前 20000 字
```

即：

```python
hay_title = title or ""
hay = f"{hay_title}\n{text[:20000]}"
```

这样设计是为了兼顾速度和召回：

- 标题通常最能反映文件主题。
- 正文前部通常包含发文依据、适用对象、政策目标和主要措施。
- 全量文件约 84GB，如果每条都全文深扫，会显著降低处理速度。

## 4. 候选评分规则

当前默认阈值为：

```bash
--min-candidate-score 3
```

评分规则如下：

| 规则 | 分值 | 说明 |
|---|---:|---|
| 没有强新能源汽车词，且没有弱词近邻命中 | 直接 0 分 | 不进入候选 |
| 命中强新能源汽车词 | `2 + min(3, 强词去重命中数)` | 最多贡献 5 分 |
| 命中任意弱词近邻规则 | `+1` | 弱召回，只加一次 |
| 命中政策语境词 | `+min(3, 政策词去重数 // 2 + 1)` | 最多贡献 3 分 |
| 标题中命中强新能源汽车词 | `+3` | 标题命中权重更高 |
| 命中误伤提示词 | `-1` | 降低会议、培训、公示等误伤 |

一个文件只要最终分数达到 3，就进入候选池。候选池会保留 `candidate_score`、`nev_keyword_hits`、`policy_keyword_hits`、`text_char_len` 等字段，便于后续复核。

## 10. 候选文本片段 `llm_body` 的生成

进入候选池后，脚本不会把完整正文都送给本地模型，而是生成一个压缩后的 `llm_body`。

如果正文长度不超过上限，直接使用全文。否则使用以下片段：

1. 正文开头最多 1200 字。
2. 每个新能源汽车关键词附近的窗口。
3. 正文末尾最多 700 字。
4. 合并重叠窗口。
5. 控制总长度不超过 `--max-body-chars`。

随机 1000 测试脚本当前设置：

```bash
--max-body-chars 3500
```

这样能让模型看到政策主旨、关键词上下文和结尾条款，同时控制分类成本。

## 11. 随机 1000 条候选的抽样逻辑

用户要求的是从 BeautifulSoup 初筛出的新能源汽车相关候选中随机抽 1000 条，而不是取前 1000 条。

当前使用 reservoir sampling：

1. 流式扫描全量 JSON 文件。
2. 对每条记录做 BeautifulSoup 清洗和候选评分。
3. 只有达到候选阈值的记录才进入候选池。
4. 前 1000 个候选直接保留。
5. 从第 1001 个候选开始，每来一个新候选，都以等概率替换样本池中的某条旧候选。
6. 全量扫描完成后，样本池中的 1000 条即为候选池的随机样本。

当前随机种子：

```bash
--sample-seed 20260604
```

这样同一输入、同一脚本版本、同一随机种子下，可以复现同一批随机候选。

## 12. 与最终产业政策判断的关系

BeautifulSoup 和关键词规则只回答一个问题：

```text
这条法规是否值得交给模型进一步判断为新能源汽车相关候选？
```

它不直接回答：

```text
这条法规是否一定是新能源汽车产业政策？
```

最终产业政策判断由本地模型完成，且采用对抗策略：

- 先寻找“它不是新能源汽车产业政策”的最强理由。
- 再综合标题、发文主体、法规类型、正文片段和政策措施判断。
- 三个模型分别判断，然后按严格多数形成共识。
- 没有形成多数的样本不直接进入面板，或者留给人工复核。

## 16. 当前规则的优点和局限

优点：

- 高召回：强词和弱词近邻结合，能捕捉多种新能源汽车表达方式。
- 可解释：每条候选都保留命中的关键词和候选分数。
- 可扩展：可以直接增加关键词、近邻规则或误伤扣分词。
- 可复现：随机抽样使用固定随机种子。

局限：

- 标题或正文前 20000 字之外出现的关键词不会参与候选评分。
- “智能网联汽车”可能包含非新能源汽车内容，因此仍需模型二次判断。
- “动力电池”“充电设施”等词可能出现在非汽车场景中，因此设置了政策语境词和误伤扣分，但仍可能有少量误召回。
- 候选阈值越低，召回越高但误报越多；阈值越高，误报越少但可能漏掉措辞隐晦的政策。

## 17. 调参建议

如果希望提高召回：

- 降低 `--min-candidate-score`，例如从 3 调到 2。
- 增加弱词近邻规则。
- 增加行业相关强词，例如特定的电池、氢能、充电运营术语。

如果希望减少误报：

- 提高 `--min-candidate-score`，例如从 3 调到 4。
- 增加误伤扣分词。
- 对“智能网联汽车”“动力电池”“充电设施”等词增加更严格的近邻限制。

当前随机 1000 测试建议先保持阈值 3，用模型分类结果估计误报率和漏报风险，再决定是否调参。
